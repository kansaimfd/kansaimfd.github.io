# 鮮度確認の手順書

登録済みの施設が**今も公式の情報と合っているか**を確かめ、食い違いを直す PR を出す手順。
毎週の定期実行（Claude Code のスケジュール実行）が読んで、そのとおりに動く。人が手で回してもよい。

新しく施設を調べる手順は [research-brief.md](./research-brief.md)。こちらはその**再確認版**で、
調べる側の原則（公式サイトのみ・書いていないことは推測しない・数値は原文で裏取り）はあちらに従う。

## なぜ要るか

月次の鮮度検査（`audit-freshness.mjs`）が出すのは「確認から1年を超えた施設の一覧」までで、
中身が変わったかどうかは見ない。休館・移転・貸館の終了・料金改定は告知なく起きるので、
**開くけれど中身が変わった施設**は、誰かが公式を読み直さない限り見つからない。

## 役割の分け方

| 役 | モデル | やること |
| --- | --- | --- |
| 親 | Opus | 実行してよいかの判断、対象の選定、子の報告の裏取り、YAMLの修正、検査、PR |
| 子（1施設に1つ） | Haiku | 公式サイトを読んで、登録値と照合した結果を報告する。**ファイルは変えない** |

2026年10月に、わざと古い値を仕込んだ8施設で Haiku と Sonnet を比べた。
仕込んだ10件の検出は同じ（9件＋部分1件）で、費用は Haiku が約1/5.6だった。
一方で Haiku は**誤った主張も出す**（実際には正しく取れる出典URLを「別の市のページが返る」と書いた）。
**子の報告をそのままデータに反映しない。** 親が原文を取り直して確かめたものだけを直す。

## 1. 実行してよいかを確かめる

定期実行は週次の使用量を消費する。次のどちらかに当たれば、**何も変えずに終える**。

- 5時間枠の使用率が **60%以上**（誰かが作業中とみなす）
- 週次枠の使用率が **90%以上**（途中で上限に当たって止まるのを防ぐ）

使用率は、このセッション自身の記録にある `rate_limit_event` から読む。
`get_session`（引数なし）で自分のセッションIDを得て、`list_events` に `kinds: ["rate_limit_event"]` を渡し、
最新の `unifiedWindows.five_hour.utilization` と `unifiedWindows.seven_day.utilization` を見る（0〜1）。
**読み取れなかったときも終える。** 公開された項目ではないので、形が変わっていることがある。

読んだ値は、実行の前後とも PR 本文に残す（件数を見直すための実測になる）。

## 2. 対象を選ぶ

```bash
npm ci
node scripts/audit-freshness.mjs --json --months 0
```

`stale` が確認日の古い順に並ぶので、先頭から **10件**を採る。ただし次は飛ばす。

- **開いている鮮度確認の PR に載っている施設。** 題名が `鮮度確認:` で始まる open の PR の本文を見る。
  まだマージされていないと確認日が古いままなので、そのままだと毎週同じ施設を選んでしまう
- `missing`（出典の無い施設）。照合の土台が無いので鮮度確認の対象にしない

## 3. 子に調べさせる

1施設に1つ、Haiku のサブエージェントを**並行で**立てる。渡すもの：

- 対象レコードを YAML で書き出したファイル（`出典` の `備考` も**残す**。方針で選んだ値の理由がそこに書いてある）
- 下の指示文

```text
あなたは関西の音楽施設ディレクトリの鮮度確認担当です。登録済みレコードの情報が、
現在の公式情報と比べて古くなっていないかを調べてください。

1. docs/research-brief.md と docs/freshness-check.md の「子への注意」を読み、原則に従う
2. 調査対象のレコード: <ファイルのパス>
3. 出典URLや公式サイトを辿り、各項目を現在の公式情報と照合する。
   施設そのものの状態（休館・改修・貸館休止・閉館・改称・移転・サイト消失）も確認する
4. 結果を YAML で <出力のパス> に書く（形式は下記）

施設状態: <通常 / 休止 / 閉館 / 不明 ＋根拠>
相違:
  - 項目: ...
    登録値: ...
    現在の公式値: ...
    根拠URL: ...
    原文: "<ページからそのまま引用>"
一致:
  - 項目: ...
    根拠URL: ...
確認できず:
  - 項目: ...
    理由: ...
登録に無い情報:   # 部屋・備品など、公式にあって登録に無いもの（参考）
  - ...

リポジトリのファイルは変更しないこと。curl / WebFetch は合計15回程度までに収める。
```

### 子への注意

- **相違と判断する前に、その項目の出典の `備考` を読む。** 方針で選んだ値は、公式の値の一つと違って見える
  （例：舞台幅は形式ごとの間口のうち**最大値**を採る。プロセニアム形式16.2m・コンサート形式20.8mなら20.8）
- 路線名の言い換え（東海道線 / JR神戸線）は相違ではない
- 検索結果の要約に出た値は使わない。公式ページの原文で確かめられたものだけを書く

## 4. 親が裏取りする

子の報告の `相違` と `施設状態` を、**親が curl で原文を取り直して確かめる**。

- 原文が報告どおりなら直す
- 原文が見つからない、または報告と違うなら直さない（PR の「裏取りで退けたもの」に書く）
- 「出典URLが別のページを返す」「サイトが消えた」という主張は特に疑う。2回取り直してから判断する

## 5. 直す

[data-schema.md](./data-schema.md) と research-brief.md のルールで直す。

- **確かめた相違だけ**値を直し、その出典の `備考` に新しい原文を引用する
- 照合して一致した出典は `確認日` を今日にする（相違が無かった施設もこれで「確認済み」になる）
- 次のものは**データを変えず、PR 本文に挙げて人の判断を待つ**：
  閉館・廃止の疑い、施設名の改称、部屋の追加や削除、方針の解釈が要るもの

そのあと `npm run check` を通す。通らなければ直してから出す。

## 6. PR を出す

`claude/` で始まるブランチに push し、**通常の PR**（draft ではない）を作る。題名は
`鮮度確認: YYYY-MM-DD（N件）`。本文に書くもの：

1. 確認した施設の一覧（ID・名前）
2. 直した項目と根拠（URLと原文）
3. 人の判断が要るもの
4. 裏取りで退けた子の主張
5. 確認できなかった項目
6. 実行前後の使用率（5時間枠・週次枠）

マージは人が行う。
